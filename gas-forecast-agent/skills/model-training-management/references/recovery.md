# 任务状态与恢复

## 查询选择

- 用户只提供一个无法确定类型的业务编号时，先调用 `business_reference_resolve`。
- 有 `taskNo`：先调用 `task_status_get`；用户需要步骤明细时调用 `task_steps_get`。
- 只有 `trainBatchNo`：调用 `training_status_get`。
- 查询某客户最新训练：唯一解析客户后调用 `training_latest_get`。
- 查询训练历史：唯一解析客户后调用 `training_history_get`。

## 恢复决策

| 服务端建议 | 动作 |
| --- | --- |
| `WAIT` | 任务仍在运行，只报告状态，禁止恢复或重试 |
| `RESUME` | 说明恢复位置和已有业务结果；用户确认后调用 `task_resume` |
| `RETRY` | 原批次已明确失败；说明会创建新批次，用户确认后调用 `task_retry` |
| 不可恢复 | 报告失败阶段和原因，不提供虚假的继续按钮 |

- 恢复和重试必须使用真实任务编号。
- `task_resume` 与 `task_retry` 都属于写操作，不接受模型自行生成的确认。
- 已有训练批次仍在执行时禁止重新提交。
- 请求超时但可能已经创建任务时，先查询状态；无法确认时告知“提交结果未知”。
- 新批次必须保留与原失败批次的关联，不把原记录覆盖为成功。
