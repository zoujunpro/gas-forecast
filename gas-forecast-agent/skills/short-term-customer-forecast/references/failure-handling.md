# 失败与部分成功处理

## 决策表

| 情况 | 下一步操作 |
|---|---|
| 实体结果为 `MULTIPLE` | 展示候选名称、编码、地区和行业，让用户选择 |
| 实体结果为 `NOT_FOUND` | 请用户修正名称，或补充地区、行业以缩小范围 |
| `NEED_INFORMATION` / `INVALID_ARGUMENT` | 只询问缺失或错误的字段，补充后按照同一业务意图重试 |
| `CONFIRMATION_REQUIRED` | 说明确切范围和影响，等待用户明确确认 |
| `WAITING_TRAINING` | 保存 `trainBatchNo` 并查询训练状态，禁止重新提交预测 |
| `EXECUTING` | 保存任务号或批次号，稍后查询状态 |
| `retryable: true` 且没有批次号 | 短暂等待后最多重试一次，并复用原幂等键 |
| `retryable: true` 且已有批次号 | 先查询状态，禁止再次调用启动工具 |
| `retryable: false` | 不自动重试，向用户说明具体原因和需要修正的条件 |
| 批量任务部分成功 | 继续监控已受理任务，同时单独报告失败客户 |

## 恢复含义

- `WAIT`：已有业务任务仍在运行，继续查询状态。
- `RESUME`：已有业务结果仍可使用。用户确认后从服务端给出的步骤继续；如必须调用创建类工具，应复用原幂等键。
- `RETRY`：业务批次已经明确失败，需要创建新批次。先取得用户确认，再调用 `task_retry`；服务端会保留原失败批次并关联新的训练或预测批次。

## 结果说明

- 已受理或执行中的任务不能描述成已经完成。
- 进度消息应包含客户、预测开始日期、预测天数、时间粒度和批次号。
- 返回预测明细时，应原样保留日期和单位。
- 只有服务端返回质量指标时才能解释指标，禁止把训练准确率解释为未来实际用量的保证。
- 技术错误信息应简洁，但需保留稳定错误码和具体业务原因。
